# 三档机型基线

> 归属：发布侧（路远行）。三档参数**只写在 JSON 里**，本文件只解释含义与验收方法。
> 真值源：[`Tools/build/baselines/low.json`](../../Tools/build/baselines/low.json)、
> [`medium.json`](../../Tools/build/baselines/medium.json)、[`high.json`](../../Tools/build/baselines/high.json)。
>
> 出包脚本按档位读取 JSON，把参数注入 Unity；**文档改了不算数，JSON 改了才算数**。

---

## 1. 三档速查

| 档位 | 定位 | 目标机型 | 分辨率 / 帧率 | 角色 |
|---|---|---|---|---|
| `low` | 低 · 集显轻薄本 | Intel Iris Xe 集显 / i5-1135G7 / 8GB | 1920×1080 @ 30fps | **验收底线** |
| `medium` | 中 · 入门独显 / 高配集显 | GTX 1650 / Iris Xe 锐酷 / 16GB | 1920×1080 @ 60fps | 默认发行档 |
| `high` | 高 · 主流独显 | RTX 3060 / RX 6600 / 32GB | 2560×1440 @ 60fps | 上限参照 |

**低档是硬底线**：任何档位不得低于低档参数。低档不达标 = 发行否决项，不是「优化项」。

三档参数只允许沿「分辨率 → 阴影 → 后期 → 粒子 → 贴图 → 内存」单向递增。
高档出现的可读性问题，必须在低档复现同样的判定（画面糊到看不清 ≠ 只在高档发生的问题）。

## 3. 各档的具体含义

### 3.1 low · 验收底线

- 集显轻薄本是《拾锋录》最坏的真实场景，不是「极端情况」。
- 阴影全关、后期全关、粒子上限 200、主纹理半分辨率 —— 这四刀是把集显从「勉强能跑」拉到「稳定 30fps」的主要手段。
- 纹理最大边 1024：UI 图标母版本身就是 1024×1024（AD-03 §5 的提示词模板固定 1024），
  所以低档不缩母版，靠 `masterTextureLimit=1` 在运行时降到 512。
- 脚本后端仍用 IL2CPP：Mono 在集显机器上 CPU 占用更高，帧时间尾部更差。

### 3.2 medium · 默认发行档

- 阴影开、后期开但关 Bloom（Bloom 是低端 GPU 上最贵的一项）。
- 这是**大多数玩家实际用到的档位**，发行默认出这一档。
- 若 medium 档也跑不满 60fps，先查 draw call 与粒子上限，再考虑降规格。

### 3.3 high · 上限参照

- 存在的意义有两个：
  1. 给美术一个「最高表现」环境，确认资产在上限下的样子；
  2. 给性能排查一个对照——同一个场景在 high 流畅、在 low 卡，说明是集显扛不住而非逻辑问题。
- BC7 压缩需要 DX11 及以上；`build-player.sh` 对 Windows 目标固定 DX11，避免落到 DX12 特性集。
- **高档不作为发行默认档**，但每次出包都要跑一遍，确认高档没有报错与美术破图。

## 4. 参数怎么落到构建里

```
Tools/build/baselines/<档位>.json     ← 真值源
        │  摊平成 key=value
        ▼
Tools/build/build-player.sh --tier low
        │  -buildParams <摊平文件>
        ▼
EdgeChronicles.ReleaseOps.PlayerBuild.Build（Unity 批处理）
        │  写 QualitySettings / PlayerSettings（构建期临时写，构建后还原）
        ▼
玩家包 + build-manifest.json（记录 build.tier 与 build.baselineSha256）
```

**基线改动会被记录**：manifest 里的 `build.baselineSha256` 是基线 JSON 的 sha256。
如果玩家手上的包对应的基线与现在的基线不一致，说明「性能问题」可能来自基线本身改动，
而不是某次代码提交——排查时先对这一项。

## 5. 验收方法

### 5.1 单机帧率采样

| 项 | 取值 |
|---|---|
| 采样场景 | 副本全程 + Boss 三阶段（覆盖最重负载） |
| 采样时长 | 每档 120 秒 |
| 采样工具 | Unity Profiler / `ProfilerRecorder`（帧时间）、平台工具（CPU/GPU 占用） |
| 记录项 | 平均 fps、p95 帧时、最长帧、>50ms 帧占比、draw call、三角形数 |

### 5.2 判据（与基线 JSON 的 `acceptance` 段一致）

| 档位 | 最低 fps | p95 帧时 | 长帧阈值 | 长帧占比上限 |
|---|---|---|---|---|
| low | 30 | ≤ 33.4ms | 50ms | ≤ 1% |
| medium | 60 | ≤ 16.7ms | 33.4ms | ≤ 1% |
| high | 60 | ≤ 16.7ms | 33.4ms | ≤ 0.5% |

**不达标时的处置顺序**（不要一上来就降规格）：

1. 看 draw call 与三角形数是否超了基线的 `limits` → 超了是资产/架构问题，不是画质问题。
2. 看粒子上限是否超了 `particles.maxParticles` → 超了是特效规格问题。
3. 看贴图内存与流送额度 → 超了是资产规格问题。
4. 以上都正常但帧率不达标 → 才是画质档位选择问题，再按序关：后期 → 阴影 → 各向异性 → 贴图尺寸。

### 5.3 帧率上限的落地说明

`target.targetFrameRate` 是运行期属性，**构建期写不进去**，需要运行期引导脚本生效（该脚本归工程线）。
构建期做的是：关闭 vSync（否则 vSync 会把帧率钉在刷新率上，与 30 帧上限互相打架），
并把目标帧率写进 `build-manifest.json` 的 `playerSettings`，供核对。

这一条在出包日志里会显式打为 `[BUILD] warn`，不静默通过。
