# 版本号 · 提交规范 · 分支策略

> 归属：发布侧（路远行）。本文件是版本相关的**唯一真值源**；
> 其他文档提到版本号规则时只引用本文件，不复述。

---

## 1. 版本号格式

```
MAJOR.MINOR.PATCH[-预发布标识][+构建元]
```

| 段 | 取值 | 含义 |
|---|---|---|
| `MAJOR` | 整数，0 起步 | 破坏性变更（存档不兼容 / 核心循环重构） |
| `MINOR` | 整数 | 新增玩法内容，或存档结构新增字段 |
| `PATCH` | 整数 | 修 bug、数值与文案调整、不改存档语义的优化 |
| 预发布标识 | `alpha.N` / `beta.N` / `rc.N` | 见下表 |
| 构建元 | `+<commit短哈希>` 或 `+<序号>` | 可选，同一版本号的不同构建用它区分 |

### 1.1 预发布标识

| 标识 | 含义 | 谁在用 |
|---|---|---|
| `alpha.N` | 内部可玩版，功能未定型 | 开发与自测 |
| `beta.N` | 对外测试版，功能定型、调优中 | 试玩与反馈收集 |
| `rc.N` | 候选发布版，候选清单已冻结 | 发布前的最终验证 |

**正式发行不带预发布标识**（`0.1.0` 而非 `0.1.0-rc.3`）。

### 1.2 递增规则

| 这次改动做了什么 | 版本号怎么动 | 存档 `save_version` 怎么动 |
|---|---|---|
| 只改表现：美术、配表数值、文案 | `PATCH +1` | 不动 |
| 新增养成系统 / 技传阶 / 副本机制 | `MINOR +1` | 不动 |
| 存档**新增字段**（不删、不改含义） | `MINOR +1` | `+1`，并补一级迁移 |
| 存档字段**删除或含义改变** | `MAJOR +1`（0.x 阶段为 `MINOR +1`） | `+1`，并补一级迁移 + 迁移单测 |
| 战斗核心循环重构（键位 / tick 阶段） | `MAJOR +1` | 视是否触及存档而定 |
| 纯构建 / CI / 文档改动 | 不递增版本号 | 不动 |

> **0.x 阶段的约定**：正式发行前 `MAJOR` 恒为 0，破坏性变更用 `MINOR` 承载。
> 第一次正式发行（`1.0.0`）之后，`MAJOR` 才真正开始承担破坏性语义。

### 1.3 版本号的落点

| 落点 | 来源 | 谁维护 |
|---|---|---|
| `VERSION`（仓库根） | 人工递增，出包前更新 | 发布侧 |
| `ProjectSettings/ProjectSettings.asset` 的 `bundleVersion` | 出包时由 `Tools/build/build-player.sh` 从 `VERSION` 写入，构建后自动还原 | 发布侧（构建期临时写） |
| `build-manifest.json` 的 `version.full` | 构建时从 `VERSION` 读入 | 构建自动产出 |
| `CHANGELOG.md` | 与 `VERSION` 同步更新 | 发布侧 |

**硬规则**：`VERSION` 与 `bundleVersion` 必须一致。资产 Gate `G7` 会在 CI 里校验这一点，不一致直接判红。

## 2. 提交粒度与消息规范

> 这一节针对的是**当前现实**：多个 AI 员工在同一工作树并行工作，
> 员工不得各自 `git commit`，由主理人统一提交。所以本节规定的是
> **「什么样的改动算一个 commit」和「消息怎么写」**，让统一提交的人有据可依。

### 2.1 一个 commit 的判定

**一个 commit = 一个能独立说清楚、能独立回滚的改动单元。**

该拆的判据（满足任一即拆）：

| 情形 | 拆法 |
|---|---|
| 跨模块且彼此独立（引擎代码 / 配表 / 美术资产 / 文档 / CI） | 按模块拆 |
| 一个改动里混了「加功能」和「顺手重构」 | 先提重构（`refactor`），再提功能（`feat`） |
| 引擎逻辑改动与配表数值改动同批提交 | 拆开：数值单独一个 `data` 或 `chore(data)` |
| 美术「母版」与「切片/图集」分开提交 | **不拆**：图集与切片必须同批，否则对不上 |
| 功能实现与它的单测分开提交 | **不拆**：测试随功能走 |

不该出现的情况：

- 一个提交同时改了战斗逻辑与 UI 布局（除非它们本来就是一件事）。
- 提交里混进生成物（配表产物 `Assets/_Project/Data/*.json`、`Library/`、构建产物 `Build/`）——这些不入库。
- 提交里混进**不属于本次改动**的文件（并行工作树的常态，必须逐路径 `git add`）。

### 2.2 消息格式

```
<type>(<scope>): <简述>

<正文：这个改动为什么存在、影响什么、怎么验证>

Refs: <任务号>
```

- `<type>`：`feat` `fix` `refactor` `perf` `docs` `build` `ci` `test` `chore` `data` `assets`
- `<scope>`：模块名，约定用 `battle` `data` `progression` `save` `ui` `presentation` `art` `build` `docs` `ci`
- `<简述>`：中文祈使句，一句话说清改了什么，不超过 50 字，不以句号结尾
- `<正文>`：写**为什么**和**怎么验证**，不复述 diff；有破坏性变更单独起 `BREAKING CHANGE:` 段
- `Refs:`：填任务号，例如 `Refs: EC-S1-RO-01`

示例：

```
feat(progression): 技传阶位派生解锁接入技传表

IMPL-v3.0 §4.5.2 的 8 条派生条目此前只落在文档里，运行时无法触发。
本次把 unlock_derivative_id 写进技传表并接上求值器，迅锋 3 阶「回响」
可实际产生第二道刀光。

验证：bash Tools/ci/check-progression.sh 通过；PlayMode 断言
Kernel.Tests.TechTierLinkTests 全绿。

Refs: EC-S1-EL-02
```

### 2.3 统一提交时的动作顺序

主理人提交时按这个顺序拆与提：

1. `git status --short` 收集全部改动（并行工作树会有多个来源的文件）。
2. 按 §2.1 的判据分组，每组用**明确路径** `git add -- <路径1> <路径2>`，禁止 `git add -A` / `git add .`。
3. 每一组提交前 `git diff --cached --stat` 复核，确认没有夹带他人无关改动；发现夹带 → `git restore --staged` 后重来。
4. 组内提交顺序：`refactor` → `feat` → `fix` → `test` → `data` → `assets` → `docs` → `build`/`ci`。
5. 每提一个，`git status --short` 复核一次；出现意料之外的文件立刻停下核对来源。
6. **不做** `git push --force`、不 `git reset --hard` 覆盖别人的工作树。

## 3. 分支策略

### 3.1 模式 A：单工作树 + 主理人统一提交（当前现实）

**为什么是这种模式**：

- 多个 AI 员工在同一工作树上并行写文件，任何一个员工自行 commit，都可能把别人**尚未完成的中间态**一起提交进去。
- `.unity` / `.prefab` 是文本但极易冲突，正确的解法是 UnityYAMLMerge；而 AI 员工的中间态经常是「场景改了但脚本还没改」，合并冲突后无法判断该保留哪一侧。
- 强制 PR 反而会把「半成品必须能编译」这条硬要求提前到每个中间提交上，与并行切分的做法冲突。

**模式 A 的规则**：

| 规则 | 说明 |
|---|---|
| 员工不改版本控制状态 | 任何员工都**不得**执行 `git commit` / `git push` / `git checkout` / `git switch` / `git reset` / `git stash` / `git clean`——这些会抢走别人工作树的状态 |
| 员工只改文件 | 允许：新建、修改、删除工作树内的文件 |
| 主理人统一提交 | 按 §2.3 的动作顺序提交 |
| 提交粒度由 §2.1 判定 | 不按「谁改的」拆，按「改动单元」拆 |
| 每次提交后必查 | `git status --short` 必须能看到预期的剩余改动 |

**模式 A 的已知代价**（接受它，因为当前阶段收益更大）：

- 提交历史里会混杂多个模块的改动（靠 §2.1 的拆分与消息规范缓解）。
- 无法用「分支」隔离半成品，冲突在主理人提交时才暴露。
- 缓解手段：员工改文件前先 `git status` 看一眼，避免动到别人正在改的同一文件；真撞了就先在群里对齐。

### 3.2 模式 B：分支 + PR（人类流程）

一旦进入「有人类直接参与提交」的状态，就切到模式 B：

| 项 | 规则 |
|---|---|
| 分支命名 | `feat/<简述>` `fix/<简述>` `chore/<简述>` `release/<版本号>` |
| 合并方式 | **squash merge**——一个 PR 一个 commit，`main` 历史保持线性 |
| `main` 保护 | 必须 PR + CI 全绿 + 至少一次审阅；**禁止直推** |
| `release/<版本号>` 分支 | 从 `main` 切出；只接受 `fix` / `chore(build)` / `chore(ci)` 类 PR；出包从它打，manifest 记录分支名 |
| 合并前检查 | `git status` 干净；`Tools/ci/check-*.sh` 全绿；资产 Gate 通过 |
| 发布分支的处理 | 发行后打 tag（`v<版本号>`），release 分支合回 `main` 并删除 |

### 3.3 两种模式的切换条件

| 从 A 切到 B 的触发条件 | 理由 |
|---|---|
| 有人类开始直接向仓库提交 | 人类需要自己的审阅点与可回退的分支 |
| 仓库转为公开 / 需要外部协作 | 公开库必须开分支保护与审阅 |
| 两个员工开始频繁改同一批文件 | 合并冲突的代价超过 PR 带来的收益 |
| 进入发版冻结期 | 需要「只进修复」的分支来隔离风险 |

**从 B 切回 A 的条件**：没有人类直接提交，且并行冲突频率重新下降。

切换动作：把 `main` 的分支保护规则调整，并在本文件 §3.1 / §3.2 标注当前生效模式。
**同一时刻只允许一种模式生效**，避免「一半提交走 PR、一半走统一提交」的历史断层。

## 4. 与构建流程的衔接

```
VERSION ──出包──▶ PlayerSettings.bundleVersion（构建期写入，构建后还原）
      │
      └──▶ build-manifest.json.version.full ──▶ 补丁说明里的版本号
```

出包脚本：`Tools/build/build-player.sh`（详见 [`Tools/build/README.md`](../../Tools/build/README.md)）。
产物校验：`Tools/build/verify-artifact.sh`（用 manifest 的校验和判定「装的是不是这一版」）。
发布与回滚清单：[`RELEASE-CHECKLIST.md`](./RELEASE-CHECKLIST.md)。
